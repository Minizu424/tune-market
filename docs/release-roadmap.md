## 0. 全体の考え方

現状は「機能は揃っているが、経済とセキュリティがクライアント任せ」という状態である。
一般公開までの作業は、機能追加よりも以下の3点に集中する。

1. **サーバー側の不在を埋める**（不正ができない状態にする）
2. **経済設計の穴を塞ぐ**（価格モデルとポイント総量）
3. **法務・審査の要件を満たす**（UGC・著作権・規約）

その上で、コンセプトを成立させる機能（株主特典）を乗せる。
作業には依存関係があり、順番を間違えると作り直しになる。

```text
価格モデル刷新 ＋ Cloud Functions 移行
        ↓
権利確定日スナップショット基盤
        ↓
株主投票 / 壁紙・ボイス配布 / 投資家プロフィール
```

### 0-8: ライト基調への刷新

暗い配色は「暗いこと」より**面同士の明度差が小さすぎること**が問題だった。
背景 `#061226` / カード `#111827` / 罫線 `#1F2937` では、カードが下地から浮いてこない。

トークンを2系統に分けて解決した。

- `Colors` …… ライト基調。アプリの大半
- `OverlayColors` …… ジャケット画像の上に重なる画面（リール・ミニプレイヤー・コメントシート）

**リールを明るくできない理由**: ジャケットを全画面に敷いて文字を重ねる構造のため、
明るいUIだと写真の上で可読性が失われる。ライブラリは明るく再生画面だけ暗い、という
音楽アプリ共通の構造をそのまま採用した。

キー名を2系統で揃えてあるので、暗いままにする画面は import を読み替えるだけで済む。

コントラストは機械検査で担保している（**51組すべて WCAG AA 4.5:1 以上／最低 4.56:1**）。
検査の過程で `textFaint` と `gold` が背景 `#F1EFE9` の上で 3.9〜4.0:1 しかなかったため、
それぞれ `#6F6C65` / `#956108` まで落として基準を満たした。

手順は `docs/demo-runbook.md` を参照。

### 0-1: 需給による価格インパクト

```text
変動率 = 取引額 / (板の厚み + 取引額)      板の厚み = 400pt、1取引の上限 ±25%
```

| 購入額 | 100ptの株が | 変動率 |
|---|---|---|
| 10pt | 102pt | +2.4% |
| 50pt | 111pt | +11.1% |
| 100pt | 120pt | +20.0% |
| 200pt以上 | 125pt | +25.0%（上限） |

- 売却は同じ式で下落する
- 取引ごとに `priceHistories` に記録するので、チャートがその場で伸びる
- **板の厚み400ptはデモ用に敏感めの値**。本番では取引量に応じて引き上げる

#### 約定価格を平均にした理由（無リスク裁定の潰し込み）

当初は「取引前の価格で約定 → そのあと価格が上がる」という実装にしていたが、
これだと**買った直後に売るだけで確実に儲かる**。124ptで買って138ptで売れてしまうため。

実際の板取引と同じく、価格を押し上げながら約定していく**平均約定価格**を使うように変更した。

```text
平均約定価格 = (取引前価格 + 取引後価格) / 2
```

検算（124ptの株を50pt購入 → 即売却）:

| | 平均約定 | 価格の動き | 残高 |
|---|---|---|---|
| 買い | 130.89pt で 0.382株 | 124 → 138pt | 100 → 50pt |
| 売り | 129.97pt で 49.65pt | 138 → 122pt | 50 → 99.65pt |

往復で **-0.35pt**。往復売買にコストがかかり、裁定は成立しない。

なお本番では、ここにさらに **売買手数料1〜2%**（Phase 1-2）を上乗せして、
ポイント総量の回収弁とする必要がある。

### 0-3: 発見したバグ（重要）

`getPriceHistories` が `orderBy("recordedAt", "asc") + limit(60)` になっていた。
Firestore の limit はクエリ順の先頭から取るため、これは**最古の60件**を返す。
つまり履歴が60件を超えた時点で、チャートに新しい価格が永久に出なくなっていた。

`desc + limit` に変更し、取得後に反転させる形へ修正。
この変更で `(songId ASC, recordedAt DESC)` の複合インデックスが必要になったため、
`firestore.indexes.json` を追加した。インデックス未作成でも画面が壊れないよう、
全件取得してクライアント側でソートするフォールバックも入れてある。

### Firestore の実データ調査で分かったこと

発表前に本番データを確認したところ、**シード8曲のうち7曲が初期価格100ptを割っていた**
（最安 Midnight City 39pt）。原因は `NO_ACTIVITY_DECAY = 0.99`。
株価更新ボタンを押すたびに反応のない曲が1%ずつ下がり、90回以上の更新で複利的に減衰していた。

- 価格チャートが全曲右肩下がりで、ポートフォリオは含み損
- 「応援すると価格が上がる」という主張をデータ自身が否定する状態だった

→ `scripts/seed-demo.mjs` でシード8曲のみ作り直した（実データの「団子」「ピエロ」は保持）。

またこの調査で、以下も判明した。

- **団子の `totalPlaySeconds` が12,119秒（約3.4時間）**。リールを開きっぱなしにした時間が
  そのまま加算されており、**放置するだけで価格が上がる**状態。再生時間の計上に上限が要る
- **団子の `jacketUrl` が大阪芸術大学サイトの画像への直リンク**。
  Phase 1-4 で挙げた「外部URL方式の著作権リスク」がそのまま実例として発生していた

## Phase 2: コンセプトを成立させる機能

「株を持つ意味」が現状は値上がり益しかない。ここを埋めないと、公開しても定着しない。

### 2-1. 権利確定日スナップショット（特典の親機能）

**設計の核心**。「売ったら特典はどうなるか」への回答。

- 毎月末など権利確定日を定め、その日の保有状況をスナップショットとして保存する
- 特典はスナップショット対象者に配布し、受け取ったコンテンツは永久に残る
- 現実の株主優待と同じ仕組みのため、**権利付き最終日の駆け込み買い**と**権利落ち**が自然に発生する
- 「権利を取ってから売る」は株主優待文化では正当な行動として認知されているため、「売る＝推しへの裏切り」という気まずさを回避できる

実装: `holdingSnapshots` コレクション ＋ Cloud Scheduler での定期実行。
ティアは「株数」ではなく **保有額** または **その曲の保有者内での順位** で切る（端数購入があり発行株数の概念がないため）。

### 2-2. 株主投票 — **Phase 0 で実装済み**

次のジャケット、曲名、MVの方向性などを、**保有株数に比例した票数**で決める。

**データ構造**

```text
songs/{songId}/polls/{pollId}              設問と選択肢ごとの集計
songs/{songId}/polls/{pollId}/ballots/{userId}   投票用紙
```

- サブコレクションにしたのでコメントと同じく複合インデックスが不要
- **投票用紙のドキュメントIDをユーザーIDにすることで、二重投票を構造的に防いでいる**
- 投票の変更も可能（トランザクション内で前の票を差し引いてから加算するため、集計がずれない）
- 株を保有していないユーザーは投票できない（`holdings` をトランザクション内で確認）

**残っている課題（本番まで）**

- 集計をクライアントが直接更新しているため、票数を改竄できる。Cloud Functions へ移行が必要
- 投票の作成が「署名済みユーザーなら誰でも」になっている。アーティスト本人に限定すべき
- 締切（`status: "closed"`）を切り替えるUIが未実装
- 権利確定日（2-1）と組み合わせて「確定日時点の保有株数で投票権を決める」形にすると、
  投票直前に買って直後に売る行為を防げる

※ README の「議決権は発生しません」は金融商品としての議決権の話であり、クリエイティブへの投票は別物。
アプリ内にもその旨を明記している。

### 2-3. 段階的な株主特典

| ティア | 特典 |
|---|---|
| 全株主 | デジタル株主証明書（保有額・保有開始日・「第◯番目の株主」入りカード、SNSシェア可）／「創業株主」バッジ（上場24時間以内）／株主限定の制作進捗／貢献者ランキング掲載 |
| 中位 | 壁紙・ロック画面用アート／未公開音源・デモ版・インスト版／歌詞の手書き画像 |
| 上位 | アーティストからのボイスメッセージ（月1・1〜2分）／株主投票権 |
| トップ | 名前を呼ぶ個別ボイスメッセージ（上位5人など）／手書きサンクスカード／ライブ・物販の先行 |

**留意点**

- 壁紙・ボイスはアーティストの継続負担が重い。まとめ録りできるUI、ジャケットからの壁紙自動生成など、負担を下げる仕掛けとセットで実装する
- 特典コンテンツにはユーザーIDの透かしを埋める（流出は起きる前提）
- 抽選型特典は**懸賞**、全員配布は**総付景品**として景表法の規制対象。ポイントが有償になった時点で効いてくる
- ティアに上限を設け「これ以上積んでも特典は増えない」と明示する（射幸性対策）
- ボイス・画像の二次利用禁止を規約に明記

### 2-4. 投資家の可視化

株の面白さの半分は「他人と比べられること」であり、現状これが無い。

- 投資家プロフィール＋公開ポートフォリオ（公開／非公開を選択可）
- **リターン率ランキング**（総資産ではなく利回り。新規ユーザーにも勝ち目が出る）
- **目利きスコア**: 保有者数が少ないうちに買った曲が伸びた率。「まだ誰も知らない曲を掘る」動機を作り、無名アーティストに人を流す。プラットフォームの生命線
- 投資家のフォロー、フォロー中の人が買った曲の通知

### 2-5. アーティストが参加する理由

供給側がいなければ市場は成立しない。無名アーティストにとっての見返りを先に用意する。

- **再生離脱ヒートマップ**: `totalPlaySeconds` を秒単位で取れば「サビ前で何割が離脱したか」が出せる。Spotify for Artists でも見られない粒度で、**アーティストがこのアプリを使う理由そのもの**になり得る
- 曲のバージョン履歴（demo → v2 → 完成）
- ファンの熱量が数字で見える（誰がどれだけ応援しているか）
- 応援ptの出口（現金化不可でも、機材クーポン・スタジオ利用料・ディストリビューション手数料への充当なら成立）

## 補足: 最大のリスクは技術ではない

音楽プラットフォームは供給側（アーティスト）が0人だと即死する。
Tune Market のターゲットは無名アーティストであり、「有名人を呼ぶ」という逃げ道がない。

最初の10人は、軽音サークル・DTM界隈・友人の紹介を1人ずつ手で口説くしかない。
そのため、**実装を進めるのと並行して、アーティスト1人に30分ヒアリングする**ことを強く勧める。
実装コストゼロで、作るものの精度が上がる。
